## 1. What this study is and is not

Tila's engineering is credible, but the repository has not shown that it improves
real parallel coding-session work. This pilot is the smallest legitimate attempt:
real coding agents, separate git worktrees on one Linux host, frozen external
acceptance tests, the same budgets with and without tila, and every outcome kept.

It is a **deterministic-where-possible local study**, not the multi-host
authenticated case study. The two are kept apart on purpose:

| Question | Where it is answered | Provenance |
|---|---|---|
| Does the local harness work, and is this run's store wired correctly? | unit tests and preflight drills against scratch stores | `harness_fixture` |
| Do agents with tila do better on bounded parallel coding work, on one host? | this pilot's four trials | `local_agent_trial` |
| Does a Mac/Linux orchestrator–worker flow work against an authenticated Cloudflare project? | #283 and #308 S1–S3, run elsewhere | `linked_external` (linked, never re-labelled) |

What the pilot **cannot** show, whatever the numbers say: deployed latency;
multi-host or native-session recovery; native context compaction; authenticated
live memberships and key-only auth; MCP workflow cost; behaviour beyond two task
types, one model family and one operator. A small sample does not support a broad
conclusion; the report must say so next to every comparison.

It does not satisfy #283, #308 or #292. A bounded local multi-worktree study is a
legitimate #194 deliverable on its own terms; the live gates keep their owners.

## 3. Design at a glance

| Element | Declaration |
|---|---|
| Conditions | **A** baseline (git worktrees, shared Markdown board/decisions/handoffs, same channel) vs **B** A plus tila (local backend) |
| Participants | one orchestrator (scripted, not a subject) and two coding workers `w1`, `w2`; a replacement `w1r`/`w2r` after the checkpoint |
| Model and effort | GPT-6.1-Sol, `high`, identical for both conditions and every worker; exact model id recorded at freeze |
| Host | one Linux host, one run-owned directory, separate git worktrees per worker |
| Budgets | 12 minutes wall per trial; 40 admitted hook-covered operations per worker role per trial (inclusive of its replacement); claim TTL 120 s |
| Pairs and variants | `p1` (report) and `p2` (commands), each with matched variants `x` and `y` |
| Order | `t1 = p1/A`, `t2 = p1/B`, `t3 = p2/B`, `t4 = p2/A` (A/B then B/A) |
| Variant allocation | seeded: `sha256("tila-194-pilot-v1|<pair>")`, low bit of the first byte picks which variant runs under A |
| Roles | items swap between `w1` and `w2` between pairs; each condition has one trial replacing `w1` and one replacing `w2` |
| Freshness | fresh clone, worktrees, tila store and agent contexts per trial; no memory carried over |

The pilot limits (two pairs, 12 minutes, 40 hook-covered operations, Sol `high`) are scheduling
and capacity choices declared for prospective v3 execution in commit
`5b8aaf9601ebb331f98397535498ff456dbd09f3`. They are not measured values and are
not tuned afterwards. Bounds are never extended after an outcome is seen.

### Learning and order effects

- Condition order is counterbalanced across pairs: A then B in `p1`, B then A in `p2`.
- Every context is fresh; no transcript, solution or memory crosses trials.
- Both conditions get equal training time and equally usable examples and an unscored warm-up on a throwaway
  fixture. Setup time and steps are recorded per condition and not scored.
- With two pairs, order and pair are confounded and no statistical adjustment is
  attempted. Results are reported by trial position as well as by condition.
- Operator familiarity improves over time and is not controllable; operator minutes
  are logged per trial so the drift is visible.

## 4. Conditions and tool surfaces

| Duty (identical in both) | Condition A | Condition B |
|---|---|---|
| Claim the shared helper before editing | atomic `mkdir` lock with a named owner; record ownership/transfer on the board | `sdk … claim` on the helper task (public SDK facade; a loss is a 409) |
| Acknowledge a decision change | ordinary Markdown ACK, written and confirmed by `board ack <id>` | fenced `task update` of own item with the decision id, via the CLI |
| Save a handoff at the checkpoint | `shared/HANDOFFS/<role>.md` with the six fact fields | `sdk … handoff-create` (summary plus references) |
| Resume as a replacement | read the condition's durable resources, write `RESUME.txt` | `sdk … reentry`, read task state, write `RESUME.txt` |
| Declare a result | `board result <commit>` appends and confirms an explicit Markdown RESULT | fenced single-field `task update --field result_commit=<sha>`; status is a separate update |

Condition B uses:

- the **source CLI** (`bun`, from this checkout, started in each worktree so
  `.tila/config.toml` is discovered) for `task show/list/update --fence`, `state`,
  `artifact` and `journal` reads; and
- a **thin logged wrapper over the public local SDK facade**
  (`buildLocalResources`) for claims, handoffs and reentry. It adds no behaviour: no
  retry, reassignment or recovery logic. It exists because handoffs and reentry
  have no local CLI surface, and because at declaration time the CLI's `task
  claim` mis-reported a lost claim. The source CLI now rejects a lost claim after
  a separately delivered fix; the declared SDK selection is retained (see
  [coverage limits](#13-coverage-limits-and-known-limitations)).

Both conditions get the same `NOTES.md` baseline durable notes, the same packets
apart from the condition appendix, the same communication channel, and no
agent-specific tooling beyond the above. Markdown files remain available in B;
whether workers also used them is logged (cross-use), not forbidden.

## 5. Tasks

Both templates are real, small coding tasks in a disposable repository generated
from `scripts/dogfood-study-fixtures.mjs`. Acceptance tests, reference solutions
and fact sheets are generated by the same module, hashed in the manifest and never
placed in a worktree. No production backlog work is scored.

| Pair | Template | Item 1 / Item 2 | Injected overlap | Mid-trial decision change (D0 → D1) |
|---|---|---|---|---|
| `p1` | report | a summary report / a single-record detail view | both need one new shared amount formatter | negative amounts and large amounts change rendering |
| `p2` | commands | a `list` subcommand / an `export` subcommand | both need one new shared flag parser | unknown flags change from ignored to a usage error (exit 64) |

Matching: variants of a pair have equal file layouts, equal numbers of acceptance
cases and reference-solution size within 15 percent, with different identifiers,
data, output wording and file names. The fixture validator checks this before
freeze and the manifest records the hashes.

Frozen acceptance tests carry tags: per-role subsets (`item1`, `item2`), cross-role
(`x`) and decision-sensitive (`D1`). A worker that ignores D1 passes its pre-D1
reading of the task and fails the `D1` assertions: that is how a lost decision
becomes visible.

## 6. Trial script

All offsets are from T0, when both workers have received their packets.

| Offset | Event | Notes |
|---|---|---|
| 0:00 | packets delivered (`packet.delivered`) | start skew between workers must be ≤ 30 s |
| 0:00 → | overlap opportunity exists by construction | one shared helper needed by both items |
| 4:00 | orchestrator issues D1 (`decision.issued`) | each worker must acknowledge in its system of record (`decision.acked`) |
| 5:30 | handoff checkpoint requested for the replaced role | `handoff.saved` |
| 6:00 | replaced role's context ended with **no release step**; fresh context with a distinct participant id starts (`recovery.started`) | its claims expire by TTL, as a real lost session's would |
| 12:00 | hard stop | outcome recorded; both branches collected |

After the stop the harness integrates `w1` then `w2` onto the base in a scratch
clone, does **not** resolve conflicts, runs the frozen tests, audits paths, and
writes `evaluation.json`. The replacement shares its role's budget and worktree.

Pre-D1 results are provisional. D1 and the replacement still occur on schedule;
a completed replacement may verify and reaffirm without needless edits. Scheduled
D1, handoff request and replacement start have a 15-second lateness tolerance.
Replacement startup and claim expiry use the same wall clock; no pause or extension.

Record the original context stop before registering its replacement session. A
replacement is never inferred from an unknown session ID. At the deadline close
admissions, stop only the trial's outstanding activity and preserve committed,
uncommitted and shared-state snapshots before evaluation. Post-deadline work is
excluded; inability to establish the deadline state makes the trial invalid.
Evaluation uses run-owned branch reflogs to retain each commit's origin; a missing
origin refuses evaluation. Imports do not incur authored-edit or duplication
penalties, while every unique commit is audited for immutable-path tampering.

Recovery is same-host context replacement. It is not native compaction, and the
database-reopen drill (D3) is a separate `harness_fixture` measurement.

## 7. Fairness controls

- Same model, effort, runtime, permissions, wall budget, tool-call bound,
  checkpoint schedule and baseline notes in both conditions.
- Equal training time and equally usable examples; unscored warm-up; setup effort retained.
- Packets differ only in the condition appendix. Their sha256 is in the manifest.
- The same run-owned synchronous Codex hook reserves at most 40 covered operations per base role across original and replacement contexts. Covered attempts and denials remain in the log. An unverified or incomplete hook source makes the trial `harness_invalid`; transcript counting alone does not establish admission enforcement.
- A separate GPT-6.1-Sol `xhigh` reviewer receives handoff and diff artifacts without condition labels
  where practical; whether blinding held is recorded for every scored artifact.
- The frozen evaluator directory sits outside run-visible paths; a worker reading it
  is a protocol violation, recorded and not silently ignored. The input-name guard is best effort, not OS isolation; the source checkout remains reachable by path.

## 8. Instrumentation and raw evidence

One append-only JSONL file per trial (`tila.dogfood.event/1`). Every event carries
`study_id`, `trial_id`, `seq`, `ts_utc`, `mono_ms`, `actor`, `kind`, `provenance`
and a `payload`. The shared log lock serializes admission; an old lock is never
stolen based on age. Abandoned locks cause denial and require retained failure
records and explicit cleanup outside scored work.

V3 deliberately uses **hook-covered local operations**, rather than all native
invocations. A covered Bash launch counts once, including its terminal transport
continuations; `apply_patch` counts individually. Shell subcommands do not add
slots. Code-mode wrappers add no slot beyond intercepted nested operations.
Hosted tools, subagents, external provider sessions and unsmoked specialized paths
are prohibited. The initial allowed surface is `Bash` and `apply_patch`; the same
configuration disables web search, agents, apps, plugins and MCP servers for both
conditions. Strict installed-runtime smoke must confirm the resulting surface.

[Official OpenAI hook documentation](https://learn.chatgpt.com/docs/hooks)
describes the coverage gaps: hosted tools are outside the hook path and
`write_stdin` does not repeat PreToolUse. Callback errors or timeouts can continue
a tool. Consequently no universal native-call ceiling is claimed. Enforcement of
the covered set requires the exact installed-runtime smoke plus complete private,
run-owned runtime evidence; missing callbacks or uncovered state changes invalidate
the comparison. The hook alone cannot stop an already admitted long-running tool.

| Source | Gives | Availability |
|---|---|---|
| `dogfood-study.mjs record` | scheduled deliveries, context registration/retirement, stop and interventions with both clocks | executable recorder; scripted tests are harness fixtures |
| `dogfood-study-tila.mjs sdk` / `tila` | local SDK/CLI outcomes and fences; ACK/result only after confirmed successful writes | synthetic condition-B integration coverage |
| `dogfood-study-tila.mjs board` | ordinary baseline Markdown ACK/result writes and post-write events | recorder only; no coordination service |
| Codex PreToolUse / PostToolUse | registered session, turn and invocation IDs, admission/denial and completion metadata | source adapter; installed-runtime smoke remains required |
| Native run-owned usage/call records | tokens, terminal continuations and full runtime-call totals | unavailable until supplied; no native transcript parser ships |
| Git and frozen tests | origin/import diffs, integration and per-tag acceptance | deterministic evaluator |

PreToolUse reserves slots and records metadata only. It cannot turn a grep, an
attempted append or a failed write into explicit completion. PostToolUse confirms
persisted RESUME candidates and binds time to the full note hash and invocation.
Semantic review receives that same hash; a later correction cannot backdate the
first correct decision. Structured exit status takes precedence; a Bash string
response is parsed only from its runtime header before `Final output:`, never
from command stdout. Unsupported or ambiguous success formats remain unavailable
until installed-runtime smoke establishes the format.
Result, ACK and recovery credit ends at the earliest trial closure, wall deadline
or retirement of the emitting context. Late evidence remains in the raw log and
invalidates scored state integrity; evaluator and coverage-audit events may still
be recorded after stop.
Native retries with distinct invocation IDs use separate slots; absent native retry
relationships are null, not an observed zero.

Only private run-owned records may be inspected. Published study evidence uses
synthetic participant/session labels and `$RUN`/`$SOURCE` placeholders. Remove
credentials, account/host identifiers, raw transcripts, real runtime session IDs
and absolute paths. Retain original private records for audit. Study artifacts contain experimental methods and observations only. Missing usage remains null, and subscription usage is
never converted into an observed per-run price.

## 10. Hard gates

In condition B each counter is a correctness gate on tila-managed state. A failed
gate stays failed until a corrective slice is retested. In condition A the same
counters are baseline observations.

| Gate | Counter | Threshold | Rule |
|---|---|---|---|
| G1 stale authority write | `stale_authority_accepted` | 0 | no fenced write accepted below the current fence, audited from journal order |
| G2 lost acknowledged decision | `acknowledged_decision_lost` | 0 | an acknowledged decision must survive in the result and the role's handoff or resume |
| G3 silent overwrite | `silent_overwrites` | 0 | no committed or fence-acknowledged change replaced without a recorded supersession |
| G4 inferred completion | `completions_inferred` | 0 | completion only from an explicit `result.declared` that references a result |

The recorder derives these counters from events; the validator recomputes them
from the event log and rejects a ledger that disagrees.

## 11. Outcomes, interventions and validity

Trial outcomes: `success`, `partial`, `failed`, `timeout_wall`, `timeout_calls`,
`integration_conflict`, `aborted_wrong_target_or_privacy`, `harness_invalid`.
Agent or product failures are outcomes, never exclusions.

| Level | Meaning | Effect |
|---|---|---|
| I0 | none | unassisted |
| I1 | restates the packet without new task information | assisted |
| I2 | corrective action on worker state (restart, resend, manual claim release, environment repair) | assisted |
| I3 | operator performs task work, edits worker files or resolves a merge | retained; cannot count as an agent success |

Study-level reading, fixed in advance:

| Reading | Condition |
|---|---|
| informative | all four trials valid and at most one assisted |
| inconclusive | two or more trials invalid or assisted, or any trial missing: report feasibility and limits only |
| gate failure | any G1–G4 violation in B: report it, open a bounded corrective issue, run no further trials until retested |

A harness or instrumentation failure may invalidate a comparison only by a
predeclared rule (`V-instrument`, `V-hook`, `V-start-skew`, `V-schedule`). The trial and
its evidence are retained and any replacement trial is reported separately with
`replacement_of`. Stop immediately on a wrong path, wrong target or privacy leak.

## 13. Coverage limits and known limitations

| Limit | Consequence |
|---|---|
| One host, local backend | no multi-host, authenticated, membership or Cloudflare behaviour |
| MCP is supported in explicit complete local mode but not selected here | B MCP call counts remain unavailable/null because the actual MCP workflow is not exercised; SDK/CLI calls are reported as such |
| Handoffs and reentry have no local CLI surface | B uses the SDK facade through the wrapper; an agent using only the CLI could not hand off |
| Claims in B go through the SDK facade | see KL-cli-claim-report |
| Single model family, one operator, two task types | no generality claim |
| Same-host replacement, not compaction | "resume after compaction" and "after machine change" are not measured |

Known limitations (also in the rubric):

- **KL-cli-claim-report.** At the declaration commit the local source CLI
  `task claim` prints `acquired: true` for a losing exclusive claim, with the
  holder's fence number and an epoch-zero expiry, because it does not read the
  acquire result's `acquired` flag. The SDK facade throws 409. Claim state is
  correct. This study acquires claims only through the SDK facade, never counts a
  CLI claim report as acquired, and records the CLI behaviour in the preflight
  drill. The defect is tracked and fixed separately and the study does not assume a
  corrected CLI.
- **KL-bearer-fence.** Fences are capability numbers in the existing model: a write
  presenting the current number is accepted from any participant. The study does
  not redesign this; such writes are reported as
  `holder_mismatch_current_fence_accepted`, not as stale writes.

## 14. Run procedure

The dated erratum records the current observation inventory; no retained v3 scored
bundle or successful installed-runtime smoke was established by that inventory.
`$RUN` and
`$SMOKE_RUN` are fresh disposable directories outside the checkout. `$SOURCE`
denotes the clean frozen checkout. Commands run from its root.

```bash
node scripts/generate-version.mjs cli
node scripts/generate-version.mjs sdk
# Use the committed v3 declaration; declare refuses to overwrite it.
node scripts/dogfood-study.mjs manifest-check
node scripts/dogfood-study.mjs allocate

# Prepare only throwaway warm-up fixtures before freeze, never scored variants.
node scripts/dogfood-study.mjs prepare --run-dir "$SMOKE_RUN" --trial w-A --preflight
node scripts/dogfood-study.mjs prepare --run-dir "$SMOKE_RUN" --trial w-B --preflight
node scripts/dogfood-study.mjs drill --scratch-dir "$DRILL_SCRATCH" --out "$RUN/preflight/drills.json"
```

`prepare` emits `settings-w1.json` and `settings-w2.json` with a literal `argv`
array for Codex. Inspect each array and the hook before using it. The array uses
`--no-daemon --strict-config -m gpt-6.1-sol`, `model_reasoning_effort="high"` and
invocation-local `-c` hook/tool-surface settings. It does not use `--settings` or
an unsupported `onFailure` option. Normal sandbox/approval permissions must be
identical and recorded for both conditions. Hook trust can be established by
reviewing the exact emitted hooks and adding the invocation-local hook-trust
bypass; that flag does not alter normal sandbox/approval permissions. No global configuration or authentication change is part of this procedure.

Before a worker makes its first call, record `worker.started` with its exact
run-owned runtime session ID. Unknown sessions fail admission. Example payloads
below are placeholders, not observations:

```bash
node scripts/dogfood-study.mjs record --run-dir "$RUN" --trial t1 \
  --kind worker.started --actor w1 \
  --payload '{"role":"w1","participant":"w1","context":"original","session_id":"<runtime-session-id>"}'
```

The operator runs the unscored installed-runtime smoke on both warm-up arms and
retains a private report containing source SHA, exact `codex --version`, binary
path/hash, emitted configuration template hash, identical permissions and eight
checks: coverage, identifiers, parallel 39/40/41, zero-effect denial, replacement
retirement, deadline closure, malformed/failure behavior and terminal cleanup.
Each check has `name`, `pass`, `evidence_ref` and `evidence_sha256`; references name
retained files relative to the report. `freeze` verifies the evidence and binary
hashes. A boolean attestation or source unit test cannot substitute for this smoke.

```bash
node scripts/dogfood-study.mjs freeze --run-dir "$RUN" \
  --model-id gpt-6.1-sol --count-source hook --usage-source none \
  --host-label host-1 --hook-smoke "$HOOK_SMOKE_REPORT"

# Then t1, t2, t3, t4 sequentially, in the declared order.
node scripts/dogfood-study.mjs prepare --run-dir "$RUN" --trial t1
# Register both runtime sessions; deliver packets and record the T0 barrier.
# Deliver D1 at 240 s, handoff request at 330 s and replacement at 360 s.
# Record worker.stopped before the registered replacement starts; no new allocation.
# At 720 s close admission, stop trial-owned activity and capture deadline state.
node scripts/dogfood-study.mjs record --run-dir "$RUN" --trial t1 \
  --kind trial.stopped --actor harness --payload '{"reason":"hard_stop"}'
node scripts/dogfood-study.mjs evaluate --run-dir "$RUN" --trial t1
```

Before deriving, the operator audits only each registered trial session's runtime records and records a post-stop `harness.note` with topic
`runtime_coverage_attested`, source `native_runtime_records`, `complete=true`,
all `session_ids`, `evidence_sha256`, `uncovered_state_changes=0` and
`hook_failures=0`. A missing callback, uncovered write, failure or incomplete
stream invalidates coverage; do not write a passing attestation. Hash and retain
the underlying private records. Source tests provide synthetic attestations only.

A separate Sol `xhigh` reviewer receives `review-packets/<neutral-id>.json`.
Its captured facts include the immutable task/D1 contract, existing branch commit
references, verification outcomes, handoff and RESUME text. The verdict is saved
as `trials/<trial>/review.json` with this shape:

```json
{
  "schema": "tila.dogfood.review/1",
  "reviewer": "reviewer-1",
  "blinded": false,
  "handoff": {
    "facts": {
      "goal_acceptance": "correct | incorrect | absent",
      "current_status": "correct | incorrect | absent",
      "artifact_refs": "correct | incorrect | absent",
      "verification": "correct | incorrect | absent",
      "decision_or_blocker": "correct | incorrect | absent",
      "next_owner_action": "correct | incorrect | absent"
    }
  },
  "resume": {"decision_correct": true, "text_sha256": "<packet-resume-hash>"}
}
```

These are schema examples, not verdicts. Record `blinded=false` when condition
labels or wrapper commands reveal the arm; full blinding is not assumed.

```bash
node scripts/dogfood-study.mjs derive --run-dir "$RUN" --trial t1
node scripts/dogfood-study.mjs validate --bundle "$RUN" --json
```

## 15. Remaining inputs before the first measured run under prospective v3

1. Exact installed-runtime smoke and coverage/failure evidence for the shared
   Codex surface; no source check proves runtime enforcement.
2. Two Sol `high` subject contexts at a time, plus a separate Sol `xhigh` semantic
   reviewer. The orchestrator is outside the measured subject population.
3. Exact runtime registration, on-time delivery, original-context retirement and
   replacement without counter reset; start/TTL costs consume the same wall clock.
4. Reliable termination of outstanding trial commands and preserved deadline
   snapshots. Failure to establish this state invalidates the trial.
5. Native usage and complete runtime-call records only if those metrics are to be
