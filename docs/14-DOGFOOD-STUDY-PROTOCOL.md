# Dogfood study protocol (#194)

Predeclared protocol and rubric for a paired, counterbalanced pilot that compares
parallel coding-agent work with and without tila. This document and
[`docs/evidence/issue-194-rubric-v1.json`](evidence/issue-194-rubric-v1.json) were
committed **before any measured run**. They contain design choices, not results.

| | |
|---|---|
| Status | Predeclared. No trial has run. No result exists. #194 stays open. |
| Rubric | `docs/evidence/issue-194-rubric-v1.json`, version 1, immutable (see [Change control](#change-control)) |
| Tooling | `scripts/dogfood-study.mjs` (recorder, validator, driver); fixtures generated by `scripts/dogfood-study-fixtures.mjs` |
| Pilot size | 2 matched task pairs, 4 trials, 2 coding workers per trial |
| Claim ceiling | Descriptive only. No efficacy, significance, adoption or latency claim. |

## 1. What this study is and is not

Tila's engineering is credible, but the repository has not shown that it improves
real parallel coding-session work. This pilot is the smallest legitimate attempt:
real coding agents, separate git worktrees on one Linux host, frozen external
acceptance tests, the same budgets with and without tila, and every outcome kept.

It is a **deterministic-where-possible local study**, not the multi-host
authenticated case study. The two are kept apart on purpose:

| Question | Where it is answered | Provenance |
|---|---|---|
| Does the local harness work, and is this run's store wired correctly? | unit tests and preflight drills against scratch stores | `harness_fixture` |
| Do agents with tila do better on bounded parallel coding work, on one host? | this pilot's four trials | `local_agent_trial` |
| Does a Mac/Linux orchestrator–worker flow work against an authenticated Cloudflare project? | #283 and #308 S1–S3, run elsewhere | `linked_external` (linked, never re-labelled) |

What the pilot **cannot** show, whatever the numbers say: deployed latency;
multi-host or native-session recovery; native context compaction; authenticated
live memberships and key-only auth; MCP workflow cost; behaviour beyond two task
types, one model family and one operator. A small sample does not support a broad
conclusion; the report must say so next to every comparison.

It does not satisfy #283, #308 or #292. A bounded local multi-worktree study is a
legitimate #194 deliverable on its own terms; the live gates keep their owners.

## 3. Design at a glance

| Element | Declaration |
|---|---|
| Conditions | **A** baseline (git worktrees, shared Markdown board/decisions/handoffs, same channel) vs **B** A plus tila (local backend) |
| Participants | one orchestrator (scripted, not a subject) and two coding workers `w1`, `w2`; a replacement `w1r`/`w2r` after the checkpoint |
| Model and effort | Claude Sonnet, `xhigh`, identical for both conditions and every worker; exact model id recorded at freeze |
| Host | one Linux host, one run-owned directory, separate git worktrees per worker |
| Budgets | 12 minutes wall per trial; 40 tool calls per worker role per trial (inclusive of its replacement); claim TTL 120 s |
| Pairs and variants | `p1` (report) and `p2` (commands), each with matched variants `x` and `y` |
| Order | `t1 = p1/A`, `t2 = p1/B`, `t3 = p2/B`, `t4 = p2/A` (A/B then B/A) |
| Variant allocation | seeded: `sha256("tila-194-pilot-v1|<pair>")`, low bit of the first byte picks which variant runs under A |
| Roles | items swap between `w1` and `w2` between pairs; each condition has one trial replacing `w1` and one replacing `w2` |
| Freshness | fresh clone, worktrees, tila store and agent contexts per trial; no memory carried over |

The pilot limits (two pairs, 12 minutes, 40 calls, Sonnet `xhigh`) are scheduling
and capacity choices made before observation. They are not measured values and are
not tuned afterwards. Bounds are never extended after an outcome is seen.

### Learning and order effects

- Condition order is counterbalanced across pairs: A then B in `p1`, B then A in `p2`.
- Every context is fresh; no transcript, solution or memory crosses trials.
- Both conditions get equal-length training and an unscored warm-up on a throwaway
  fixture. Setup time and steps are recorded per condition and not scored.
- With two pairs, order and pair are confounded and no statistical adjustment is
  attempted. Results are reported by trial position as well as by condition.
- Operator familiarity improves over time and is not controllable; operator minutes
  are logged per trial so the drift is visible.

## 4. Conditions and tool surfaces

| Duty (identical in both) | Condition A | Condition B |
|---|---|---|
| Claim the shared helper before editing | add `shared-helper: owner=<role>` to `shared/BOARD.md` | `sdk … claim` on the helper task (public SDK facade; a loss is a 409) |
| Acknowledge a decision change | append `ACK <id> <role>` to `shared/DECISIONS.md` | fenced `task update` of own item with the decision id, via the CLI |
| Save a handoff at the checkpoint | `shared/HANDOFFS/<role>.md` with the six fact fields | `sdk … handoff-create` (summary plus references) |
| Resume as a replacement | read the condition's durable resources, write `RESUME.txt` | `sdk … reentry`, read task state, write `RESUME.txt` |
| Declare a result | `RESULT <role> <commit>` on the board | fenced `task update --field status=done` plus the commit in the summary |

Condition B uses:

- the **source CLI** (`bun`, from this checkout, started in each worktree so
  `.tila/config.toml` is discovered) for `task show/list/update --fence`, `state`,
  `artifact` and `journal` reads; and
- a **thin logged wrapper over the public local SDK facade**
  (`buildLocalResources`) for claims, handoffs and reentry. It adds no behaviour: no
  retry, reassignment or recovery logic. It exists because handoffs and reentry
  have no local CLI surface, and because the CLI's `task claim` mis-reports a lost
  claim (see [coverage limits](#13-coverage-limits-and-known-limitations)).

Both conditions get the same `NOTES.md` baseline durable notes, the same packets
apart from the condition appendix, the same communication channel, and no
agent-specific tooling beyond the above. Markdown files remain available in B;
whether workers also used them is logged (cross-use), not forbidden.

## 5. Tasks

Both templates are real, small coding tasks in a disposable repository generated
from `scripts/dogfood-study-fixtures.mjs`. Acceptance tests, reference solutions
and fact sheets are generated by the same module, hashed in the manifest and never
placed in a worktree. No production backlog work is scored.

| Pair | Template | Item 1 / Item 2 | Injected overlap | Mid-trial decision change (D0 → D1) |
|---|---|---|---|---|
| `p1` | report | a summary report / a single-record detail view | both need one new shared amount formatter | negative amounts and large amounts change rendering |
| `p2` | commands | a `list` subcommand / an `export` subcommand | both need one new shared flag parser | unknown flags change from ignored to a usage error (exit 64) |

Matching: variants of a pair have equal file layouts, equal numbers of acceptance
cases and reference-solution size within 15 percent, with different identifiers,
data, output wording and file names. The fixture validator checks this before
freeze and the manifest records the hashes.

Frozen acceptance tests carry tags: per-role subsets (`@w1`, `@w2`), cross-role
(`@x`) and decision-sensitive (`@D1`). A worker that ignores D1 passes its pre-D1
reading of the task and fails the `@D1` assertions: that is how a lost decision
becomes visible.

## 6. Trial script

All offsets are from T0, when both workers have received their packets.

| Offset | Event | Notes |
|---|---|---|
| 0:00 | packets delivered (`packet.delivered`) | start skew between workers must be ≤ 30 s |
| 0:00 → | overlap opportunity exists by construction | one shared helper needed by both items |
| 4:00 | orchestrator issues D1 (`decision.issued`) | each worker must acknowledge in its system of record (`decision.acked`) |
| 5:30 | handoff checkpoint requested for the replaced role | `handoff.saved` |
| 6:00 | replaced role's context ended with **no release step**; fresh context with a distinct participant id starts (`recovery.started`) | its claims expire by TTL, as a real lost session's would |
| 12:00 | hard stop | outcome recorded; both branches collected |

After the stop the harness integrates `w1` then `w2` onto the base in a scratch
clone, does **not** resolve conflicts, runs the frozen tests, audits paths, and
writes `evaluation.json`. The replacement shares its role's budget and worktree.

Recovery is same-host context replacement. It is not native compaction, and the
database-reopen drill (D3) is a separate `harness_fixture` measurement.

## 7. Fairness controls

- Same model, effort, runtime, permissions, wall budget, tool-call bound,
  checkpoint schedule and baseline notes in both conditions.
- Equal-length training appendix; unscored warm-up; setup effort retained.
- Packets differ only in the condition appendix. Their sha256 is in the manifest.
- The tool-call count source (agent hook log or transcript) is declared per role
  before the run. Without a source the 40-call bound is unverified and the trial is
  `harness_invalid` for budget compliance, and the count is reported as
  `unavailable`.
- A reviewer should receive handoff and diff artifacts without condition labels
  where practical; whether blinding held is recorded for every scored artifact.
- The frozen evaluator directory sits outside run-visible paths; a worker reading it
  is a protocol violation, recorded and not silently ignored.

## 8. Instrumentation and raw evidence

One append-only JSONL file per trial (`tila.dogfood.event/1`). Every event carries
`study_id`, `trial_id`, `seq`, `ts_utc`, `mono_ms`, `actor`, `kind`, `provenance`
and a `payload`. Kinds are listed in the rubric. Tool calls and tila calls are
distinct kinds; SDK and CLI calls are never counted as MCP calls.

| Source | Gives | Availability |
|---|---|---|
| `scripts/dogfood-study.mjs record` | any event, with both clocks | implemented and tested |
| `scripts/dogfood-study.mjs tila` / `sdk` wrappers | B-condition tila calls with outcome class, resource and presented fence | implemented and tested |
| Agent tool-call log (hook or transcript) | the 40-call bound and call categories | **supplied by the run lead**; no adapter ships here |
| Native usage records | input/output/cache tokens | **supplied by the run lead** or the metric is `unavailable` |
| Git and the frozen tests | diffs, integration result, per-tag results | implemented (`evaluate`) |

No transcript parser ships with the recorder: no native usage-record format was
exercised in this environment. If native usage or tool-call logs cannot be
obtained, those metrics are published as `unavailable` with the reason; they are
never estimated as observed, and subscription usage is not converted into a
per-run price. Any price-based estimate must be labelled `estimated` with its
basis and date.

Sanitisation: synthetic participant labels, no environment dumps, credentials,
account identifiers, host addresses, private transcripts or absolute home paths
(run directories appear as `$RUN`). The validator scans for these patterns.

## 9. Metrics

Every row is reported separately; there is no composite score. Availability is one
of `observed`, `estimated`, `unavailable` or `not_applicable`; non-observed values
are `null` with a reason. The authoritative definitions are in the rubric.

| Metric | Per | A | B | Source | Availability notes |
|---|---|---|---|---|---|
| Task success (trial, role) | trial, role | yes | yes | frozen tests on harness integration | failures and timeouts stay in the denominator |
| Decision honored (D1) | trial | yes | yes | `@D1` assertions | |
| Conflict opportunities / prevented | trial | yes | yes | overlap events + diff | prevented only with evidence of a stopped or redirected attempt before duplicate edits |
| Duplicate helper definitions | trial | yes | yes | diff scan, reviewer-confirmed | |
| Reconciliation time | trial | yes | yes | overlap events | null when no overlap |
| Stale fenced writes: attempted / rejected / accepted | trial | n/a | yes | journal audit | A has no fence API; compare accepted obsolete work separately |
| Obsolete work accepted | trial | yes | yes | reviewer ledger | distinct from fence rejection |
| Holder-mismatch current-fence write accepted | trial | n/a | yes | journal audit | fences are capability numbers; an observation, not a stale write |
| Handoff completeness 0–6 | trial | yes | yes | fact sheet, token match | mechanical lower bound; human review reported separately |
| Recovery to decision / first action | trial | yes | yes | recovery events | censored at the remaining budget; wrong decisions, repeats, assists counted |
| Tool calls (by category, retries) | role | yes | yes | declared count source | unavailable without a source |
| Tokens (in/out/cache) | role | yes | yes | native usage records | unavailable otherwise |
| MCP calls | trial | n/a | **unavailable** | none | local backend rejects MCP; not exercised |
| Operator effort (active min, interventions) | trial | yes | yes | `intervention` events | unattended wait separate |
| Setup effort | condition | yes | yes | `harness.note` events | retained, not scored |

## 10. Hard gates

In condition B each counter is a correctness gate on tila-managed state. A failed
gate stays failed until a corrective slice is retested. In condition A the same
counters are baseline observations.

| Gate | Counter | Threshold | Rule |
|---|---|---|---|
| G1 stale authority write | `stale_authority_accepted` | 0 | no fenced write accepted below the current fence, audited from journal order |
| G2 lost acknowledged decision | `acknowledged_decision_lost` | 0 | an acknowledged decision must survive in the result and the role's handoff or resume |
| G3 silent overwrite | `silent_overwrites` | 0 | no committed or fence-acknowledged change replaced without a recorded supersession |
| G4 inferred completion | `completions_inferred` | 0 | completion only from an explicit `result.declared` that references a result |

The recorder derives these counters from events; the validator recomputes them
from the event log and rejects a ledger that disagrees.

## 11. Outcomes, interventions and validity

Trial outcomes: `success`, `partial`, `failed`, `timeout_wall`, `timeout_calls`,
`integration_conflict`, `aborted_wrong_target_or_privacy`, `harness_invalid`.
Agent or product failures are outcomes, never exclusions.

| Level | Meaning | Effect |
|---|---|---|
| I0 | none | unassisted |
| I1 | restates the packet without new task information | assisted |
| I2 | corrective action on worker state (restart, resend, manual claim release, environment repair) | assisted |
| I3 | operator performs task work, edits worker files or resolves a merge | retained; cannot count as an agent success |

Study-level reading, fixed in advance:

| Reading | Condition |
|---|---|
| informative | all four trials valid and at most one assisted |
| inconclusive | two or more trials invalid or assisted, or any trial missing: report feasibility and limits only |
| gate failure | any G1–G4 violation in B: report it, open a bounded corrective issue, run no further trials until retested |

A harness or instrumentation failure may invalidate a comparison only by a
predeclared rule (`V-instrument`, `V-count-source`, `V-start-skew`). The trial and
its evidence are retained and any replacement trial is reported separately with
`replacement_of`. Stop immediately on a wrong path, wrong target or privacy leak.

## 12. Relationship to S1–S3 and #283

The pilot's rubric rows were chosen so a later live study can reuse them.

| Live scenario (#308) | What this pilot covers | What it does not |
|---|---|---|
| S1 definition/settings | nothing | all of it |
| S2 orchestrator/worker assignment, questions, owner offline answer, both host directions, Mac outage, replacement | context replacement with distinct participant ids on one host; handoff and resume time; no identity crossover between `w2` and `w2r` | the managed queue's attempt/question/decision semantics (#303/#304), host directions, outage, owner escalation |
| S3 blocked/failed attention, cancellation and late-answer races, explicit completion | explicit-completion gate G4 and stale-fence rejection on one host | cancellation races, late answers, permission loss, readiness failure |

The decision change here is a plain acknowledged message in the condition's system
of record, not the managed question/decision API. #283's native-session,
cross-host and Mac-offline claims remain exclusively #283's. When #308 or #283
evidence exists, link it with `candidate_sha` and `source_ref`
(`linked_external`); never merge it into this pilot's denominators.

## 13. Coverage limits and known limitations

| Limit | Consequence |
|---|---|
| One host, local backend | no multi-host, authenticated, membership or Cloudflare behaviour |
| Local backend rejects MCP | MCP call counts are `unavailable`; SDK/CLI calls are reported as such |
| Handoffs and reentry have no local CLI surface | B uses the SDK facade through the wrapper; an agent using only the CLI could not hand off |
| Claims in B go through the SDK facade | see KL-cli-claim-report |
| Single model family, one operator, two task types | no generality claim |
| Same-host replacement, not compaction | "resume after compaction" and "after machine change" are not measured |

Known limitations (also in the rubric):

- **KL-cli-claim-report.** At the declaration commit the local source CLI
  `task claim` prints `acquired: true` for a losing exclusive claim, with the
  holder's fence number and an epoch-zero expiry, because it does not read the
  acquire result's `acquired` flag. The SDK facade throws 409. Claim state is
  correct. This study acquires claims only through the SDK facade, never counts a
  CLI claim report as acquired, and records the CLI behaviour in the preflight
  drill. The defect is tracked and fixed separately and the study does not assume a
  corrected CLI.
- **KL-bearer-fence.** Fences are capability numbers in the existing model: a write
  presenting the current number is accepted from any participant. The study does
  not redesign this; such writes are reported as
  `holder_mismatch_current_fence_accepted`, not as stale writes.

## 14. Run procedure

Nothing below has been executed as a measured run. Commands run from the
repository root. `RUN` is a new, empty directory outside the repository and
outside every worktree.

```bash
# 0. Prerequisites: pnpm install already done; gitignored generated files
node scripts/generate-version.mjs cli && node scripts/generate-version.mjs sdk

# 1. Check the declaration against the rubric and fixtures (no writes)
node scripts/dogfood-study.mjs manifest-check
node scripts/dogfood-study.mjs allocate

# 2. Preflight drills on a scratch store (harness_fixture, never agent outcomes)
node scripts/dogfood-study.mjs drill --scratch-dir "$(mktemp -d)" --out "$RUN/preflight/drills.json"

# 3. Freeze: records source sha, runtimes, model id and count source; refuses a dirty tree
node scripts/dogfood-study.mjs freeze --run-dir "$RUN" \
  --model-id <exact-model-id> --count-source <hook|transcript|none> \
  --usage-source <native_usage_record|none> --host-label host-1

# 4. Per trial t1..t4 (in order): prepare, run through the orchestrating runtime, evaluate
node scripts/dogfood-study.mjs prepare --run-dir "$RUN" --trial t1
node scripts/dogfood-study.mjs record  --run-dir "$RUN" --trial t1 --kind trial.started --actor harness
#    ... launch w1 and w2 with the rendered packets; record packet.delivered, decision.issued, etc.
node scripts/dogfood-study.mjs record  --run-dir "$RUN" --trial t1 --kind trial.stopped --actor harness \
  --payload '{"reason":"hard_stop"}'
node scripts/dogfood-study.mjs evaluate --run-dir "$RUN" --trial t1
node scripts/dogfood-study.mjs derive   --run-dir "$RUN" --trial t1

# 5. Validate the bundle before anything is published
node scripts/dogfood-study.mjs validate --bundle "$RUN" --json
```

The packets rendered by `prepare` contain the exact per-worker commands for
condition B (the `sdk` and `tila` wrappers with absolute paths), the participant
ids, and the shared directory locations.

## 15. Remaining inputs before the first measured run

1. A free coding slot for two Sonnet `xhigh` workers per trial (the three-builder
   ceiling is the user's).
2. The exact model id and a tool-call count source (agent hook log or transcript)
   for every worker; native usage records if token cost is to be reported.
3. A way to start a fresh agent context in a given worktree with a given
   participant id, deliver a message at a scheduled offset, and end a context
   without a release step.
4. A clean checkout at the frozen source sha, `bun` and `node` as listed in the
   frozen manifest, and a run directory outside the repository.
5. Optional but preferred: a second person or a label-stripping step to score
   handoffs and diffs blind.

No operator configuration, provider credential or live Cloudflare project is
needed for this pilot, and none must be searched for or mutated.

## Change control

- `issue-194-rubric-v1.json` and the declaration manifest are immutable after the
  first measured run. A change is a new `rubric_version` in a new file; the old
  file is retained.
- The frozen manifest records the rubric and declaration hashes; the validator
  rejects a bundle whose hashes disagree.
- Sections 14 and 15 of this document may be corrected for command accuracy. The
  design, budgets, metrics, gates and thresholds may not.
- A run replaced after a harness failure is reported next to the original with
  `replacement_of`; nothing is overwritten.
